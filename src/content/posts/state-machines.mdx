One boolean is easy to understand. Five independent booleans describe 32 possible combinations, including combinations that should never exist. A state machine makes the valid combinations—and the paths between them—visible.

## Name the states

Consider a small background job. It can be idle, running, completed, or failed. Instead of tracking `started`, `finished`, and `hasError` separately, give each valid condition a name.

## Encode what each state knows

A discriminated union can associate data with the state where it is meaningful. A failure has an error message. A completed job has a result. An idle job has neither.

```ts
type Job =
  | { state: 'idle' }
  | { state: 'running'; startedAt: number }
  | { state: 'complete'; result: string }
  | { state: 'failed'; error: string };

function describe(job: Job): string {
  switch (job.state) {
    case 'idle': return 'Ready to start';
    case 'running': return 'Working';
    case 'complete': return job.result;
    case 'failed': return job.error;
  }
}
```

This does not prove every transition is correct. It does prevent representing a completed job without a result, or accidentally reading an error from an idle job.

## Put transitions in one place

Treat an event as an input and the next state as an output. Keeping that function pure makes it easier to test than scattered assignments inside callbacks.

| Current state | Event | Next state |
| :--- | :--- | :--- |
| Idle | Start | Running |
| Running | Success | Complete |
| Running | Error | Failed |
| Failed | Retry | Running |
| Complete | Reset | Idle |

An unspecified transition needs a deliberate policy. Reject it, ignore it, or record it as a diagnostic. Silently inventing a new state is rarely helpful.

## Test the boundaries

Test transitions that should happen and transitions that must not happen. A second start event should not launch duplicate work. A late success event from an old request should not complete a newer one; a request identifier can help distinguish them.

Explicit states are especially useful around asynchronous work. They turn questions about timing into questions about allowed events, which are much easier to inspect.
